# 消息连接故障分析与修复

日期：2026-11-03。范围：仓库代码与部署模板审查、隔离测试；未连接生产环境，未读取生产日志。

## 结论

两个提示来源不同，不能仅凭提示认定 Redis 或消息服务宕机：

| 原提示 | 原代码触发条件 | 能确定什么 |
| --- | --- | --- |
| 消息连接已断开，定时补读中 | WebSocket `onclose` | 实时通道关闭；不能据此断言数据库消息读取失败 |
| 消息服务暂不可用 | `/api/messages/unread-count` 请求失败 | 当次 HTTP 补读失败；可能是网络、登录失效、网关或后端异常 |
| 消息服务暂不可用，定时补读中 | 领取票据、构造连接 URL 等异常 | 尚未成功建立实时连接 |

确认存在的代码问题：

1. 客户端和服务端没有心跳。服务端仅在连接成功和消息变化时发送数据，空闲期间没有上游流量。仓库 Nginx `/ws/` 设置 `proxy_read_timeout 3600s`，因此该代理链路本身可在约一小时空闲后关闭连接；外部负载均衡/CDN 若超时更短，会更早触发。HTTP 的一分钟补读不经过 WebSocket，不能给 WebSocket 续期。**这能解释空闲后断连，但不能在没有生产日志时认定它是线上唯一原因。**
2. 补读失败直接覆盖 `connection`，后续成功只更新未读数，没有恢复状态。即使 HTTP 已恢复，界面仍可能一直显示“暂不可用”。
3. 原 URL 构造不支持相对的 API base（如 `/api`）；固定重连间隔、握手无应用超时，也没有实际实现注释声称的“回到页面补读”。

仍需结合生产事实排查的配置/运行原因：

- 部署来源白名单只有 `${SAIL_SCHEME}://${SAIL_PUBLIC_HOST}`。使用 IP、另一个域名、不同协议或非默认端口访问时，Origin 必须精确匹配，否则握手可能 403。不要用 `*` 代替正确配置。
- 一次性票据有效期 30 秒；过期、重放、会话撤销、用户停用均可使握手失败。票据领取/消费及会话校验依赖 Redis。
- 同一用户在单个后端实例最多 5 个连接。第 6 个浏览器标签/窗口会被 `1008` 策略关闭；客户端重试不能突破服务端限额。
- 网关未转发 Upgrade、CDN 不支持 WebSocket、后端重启、网络切换或 DB/Redis 异常也可能产生对应错误。仓库 Nginx 已有 Upgrade 转发，不能仅看到报错就认定模板漏配。

## 已实现修复

- 每 25 秒发送 `PING`，后端通过现有并发安全 session 回复 `PONG`；10 秒没有应答则释放旧连接、重新领取一次性票据。
- 握手 10 秒超时；指数退避并加入抖动，最大约 31 秒。错误、关闭及超时共用清理逻辑，避免多条重连链；卸载/会话失效后不再连接。
- 实时状态和 HTTP 补读状态独立；一次补读成功即清除补读错误，不会假装 WebSocket 已恢复。
- 网络恢复、页面重新可见时立即补读，并检查实时连接。继续保留每分钟补读和消息变化信号触发补读。
- 支持相对 API base URL；不把长期登录令牌写入 WebSocket URL。

本次不修改生产超时或扩大来源白名单。心跳前后端协议须配套发布；旧后端不会回应新前端的 PING，应先升级后端或一并发布，再刷新浏览器。修复尚未部署生产。

## 生产最短定位步骤

1. 在出错浏览器记录实际页面 Origin、发生时间以及是否在长时间空闲后发生。
2. Network 检查 `/api/messages/unread-count` 与 `/api/messages/socket-ticket` 的状态码、响应 `message` 和 `traceId`。票据和 Authorization 属于认证材料，不复制到公开日志。
3. 检查 `/ws/messages`：101 是握手成功；403 优先比对来源；401 优先排查票据/会话；404/非 101 的 200 检查代理路径；502/504 检查上游可达性。浏览器可能只暴露 1006，仍需看代理日志，不能从 1006 推断唯一原因。
4. 若 101 后约 3600 秒无消息再断开，与仓库 Nginx 空闲超时相符；如固定在更短周期，核对实际 CDN/LB/Nginx 配置。若出现 1008，先检查该账号打开的标签数。
5. 使用 traceId 对照应用日志和同一时间段 Nginx 日志，确认 MySQL、Redis、后端重启及外部代理情况。日志分享前去掉 URL 的 `ticket` 参数。
