# 定时任务与执行记录技术选型评审

日期：2026-11-03。状态：**用户已批准按此方案实施。首期通用任务管理与执行记录已实现，支付补偿接入保留为第二步。详见 [实现与运维说明](job-scheduler.md)。**

## 建议与适用前提

建议采用 **Spring Boot Quartz Starter + Quartz JDBC JobStore + Sail 内置任务管理及执行记录**。沿用 MySQL、Sa-Token、MyBatis-Plus、Vue 管理界面，不新增独立调度服务。适用于当前模块化单体、任务主要调用本系统 Java 业务服务、单实例或少量实例部署的阶段。

如果目标已明确为“多个独立应用共享一个调度平台、跨机器路由/分片、独立运维团队”，改选 **XXL-JOB**；不建议先自己重做一套分布式调度中心再迁移。

## 评审时的现有能力与缺口

- 后端为 JDK 21、Spring Boot 4.0.9，已存在 MySQL 和 Redis 的生产部署配置。
- 消息投递 `MessageDeliveryService.Scheduler` 每轮完成后延迟 1.5 秒扫描，业务本身持久化发布任务、收件人快照、投递进度及重试信息。
- 支付 `CompensationJob` 每轮完成后延迟 60 秒扫描，已有数据库租约和续约，用于订单、退款与业务通知补偿。
- 当前缺少统一的任务定义、启停/立即执行入口、运行记录、失败检索及超时状态。已有消息发布记录、支付通知记录属于业务事实，不能当作通用任务运行记录。
- 本地环境在评审初稿时尚未安装 MySQL、Redis；同日用户已安装 MySQL 8.4.7、Redis 7.4.9，现有系统连接验证通过。批准后已实现调度模块并完成独立 MySQL 双 JVM 持久化、互斥和故障恢复验收，详见 [交付验收](job-scheduler-acceptance-20261103.md)。

## 方案对比

| 维度 | `@Scheduled` + 自建管理 | Quartz JDBC（推荐） | XXL-JOB |
| --- | --- | --- | --- |
| 适合阶段 | 少量固定后台扫描 | 单系统内可管理的持久化任务 | 多系统统一调度平台 |
| 动态任务、Cron、暂停恢复 | 需自建注册、更新和持久化机制 | 调度器已有成熟 API | 管理中心已有 |
| 持久化与集群协调 | 需自行维护租约、恢复及竞争处理 | JDBC JobStore 协调同库集群 | 调度中心与执行器协作 |
| 执行记录 | 自建 | 自建业务运行表；Quartz 表不是执行历史 | 原生调度/执行日志；与 Sail 统一展示另需集成 |
| Sail 权限和界面一致性 | 容易整合 | 容易整合 | 独立登录与权限边界，需额外设计 |
| 额外部署 | 无 | 无独立服务，新增数据库表 | 独立 admin、数据库及执行器通信端口 |
| 重试、超时 | 自建 | 业务层策略与运行记录，不能只依赖 Quartz | 平台提供策略，业务幂等仍须实现 |
| 分片及跨应用路由 | 自建成本高 | 不是首期目标 | 更适合 |
| 主要成本 | 调度正确性几乎都由项目承担 | 管理页面、业务执行记录、恢复策略 | 运维、网络、认证与 Sail UI 集成 |

Spring Boot 4.0.9 的本地依赖 BOM 管理 Quartz **2.5.2**。实施已跟随 BOM 引入 Starter，不单独覆盖版本。已核对 Boot 官方 JDBC 集成说明，并完成 Boot 4.0.9 + Quartz 2.5.2 + MySQL 8.4.7 运行与双节点恢复验证。

## 推荐方案的首期范围

### 管理界面

在“系统管理”下增加“定时任务”和“执行记录”：

- 任务列表：名称、分组、处理器、调度方式、Cron/间隔、时区、状态、上次/下次执行时间、最近结果。
- 任务配置：从后端注册的处理器白名单选择任务；参数按处理器定义校验；展示未来 5 次执行时间。
- 支持新增、修改、启用、暂停、立即执行、归档。立即执行与定时执行走同一调度和互斥流程。暂停只阻止后续触发，不承诺终止运行中的代码。
- 执行记录：任务、触发来源、状态、开始/结束时间、耗时、实例、触发人、业务处理数量、错误摘要和 traceId；支持筛选与详情。重试关联原始运行，不能覆盖失败记录。
- 权限拆分：`system:job:query/create/update/control/run/log:query`；配置变更和手工触发进入已有操作审计。默认仅超级管理员，之后按角色授权。

不开放任意类名/方法反射、Shell、SQL 或脚本输入。首期不包含 DAG、跨应用分片、工作流编排、任意线程强停及独立调度中心。

### 模块与数据

建议新建 `sail-job-api` / `sail-job-server`，由 `sail-server` 装配；API 定义 `JobHandler`、执行上下文及结构化结果。业务模块只依赖 API，通过注册 Bean 提供处理器；调度模块不直接依赖消息和支付实现，避免循环依赖。

拟用数据：

| 表/集合 | 用途与关键字段 |
| --- | --- |
| Quartz `QRTZ_*` 表 | 内部 Job、Trigger、集群节点和锁；只由调度器 API 维护 |
| `sys_job` | 任务编号、名称、处理器、参数、Cron/间隔、时区、状态、版本、并发/补触发策略、超时阈值、审计字段 |
| `sys_job_execution` | 运行编号、任务编号、配置快照、触发来源/时间、attempt、parentRunId、执行实例、操作者、心跳、起止时间、结果/计数、traceId |

业务表是任务配置的事实来源。变更提交后使调度器应用对应版本；失败时展示“待同步/同步失败”，启动和周期对账继续修复。调度执行前核对启用状态和版本，防止已暂停或已更新任务被旧 Trigger 执行。不要把“保存成功”直接等同于“调度器已生效”。执行快照保存必要参数并脱敏，不保存密钥。

Quartz JDBC schema 必须人工增量迁移，生产使用 `initialize-schema=never`。官方默认初始化脚本可能先删除已有表，不能在已有生产库使用 `always`。沿用当前项目人工增量迁移方式，不在本功能里另行替换整个数据库迁移体系。

### 执行语义与故障处理

1. 集群：相同 scheduler name、共享 Quartz 表、唯一 `instanceId=AUTO`、开启 JDBC clustering，并保证节点时钟同步。不同环境使用独立库/表，不让开发进程连生产调度库。
2. 并发：同一 `JobKey` 默认禁止并发；手工与定时触发必须使用相同 JobKey。两个不同任务定义不能因共用处理器就假定互斥，需要业务资源幂等键/租约。
3. 交付保证：按至少一次触发/可能重试设计，不能承诺恰好一次。支付与消息保留现有幂等、状态校验和数据库租约；调度器不是业务事务替代品。
4. 错过执行：默认跳过已错过的时刻；确需补偿的任务允许恢复后补一次，不无限重放停机期间的每个时间点。业务是否补偿由处理器自行按持久化数据判断。
5. 超时：标记超时、告警、请求协作取消，不能把 Java 线程中断视为业务已停止。旧任务未确认停止前不并发自动重试；崩溃恢复必须先核对租约/幂等事实。
6. 重试：默认关闭通用自动重试；只有声明可重试且幂等的处理器才允许有限次数、退避重试。复用现有业务重试时不再叠加调度级重试，避免放大请求。
7. 执行记录：开始业务工作前独立事务写入 RUNNING；结果用独立事务更新，业务回滚不能回滚执行记录。记录写入失败时不开始新工作。持续心跳与失联扫描用于将遗留 RUNNING 标成“结果未知/中断”，不能伪造失败或成功。
8. 结果：区分 SUCCESS、PARTIAL、FAILED、RUNNING、TIMED_OUT、UNKNOWN、SKIPPED。现有支付扫描会捕获单条异常，未来接入时必须返回成功/失败计数，不能凭方法未抛异常就显示整批成功。
9. 保留与性能：建议运行记录默认保留 30 天，可配置；错误摘要截断、详细日志关联 traceId、按结束时间分批清理。消息 1.5 秒一次意味着单任务每天约 57,600 次、30 天约 173 万条，必须压测和明确日志策略，不能未经评估把每次空扫描完整记入通用执行表。

## 现有任务的接入策略

建议分两步完成，不在首期同时替换所有后台循环：

- 第一步：通用调度基础、管理页面与执行记录；通过一个无副作用的演示/诊断处理器验证流程，正式上线不默认开启演示任务。
- 第二步：支付补偿经业务结果结构化后接入，迁移时关闭原 `@Scheduled` 开关，保留数据库租约并核对没有双触发。
- 消息的 1.5 秒投递循环暂保留，继续使用现有业务投递记录。若要求其也出现在统一任务页面，先提供只读内置任务状态，后续根据吞吐和日志容量评估独立接入；不直接把 fixedDelay 换成 fixedRate 或 Cron，避免改变“上一轮完成后再等一段时间”的语义。

用户按本评审方案批准实施：首期通用能力，支付接入保留第二步，消息继续原机制。

## 批准后的实施与验收

1. 验证 Boot 4.0.9 + BOM Quartz 2.5.2 + MySQL 8.4 的建表、重启恢复、双实例互斥及 misfire；明确 fixedDelay 接入方式。
2. 实现模块、迁移脚本、权限、配置对账和运行状态，再实现管理页面。
3. 验证普通用户越权、Cron/参数错误、重复手工点击、长任务重叠、运行中暂停/改配置、节点崩溃、数据库短暂故障和日志保留。
4. 在实际 MySQL/Redis 测试环境做双实例演练和容量测试；写明升级、关闭开关和回滚步骤。

回滚先停用新任务及新触发源，再回退应用；保留运行表供审计，不自动删表。不把旧 `@Scheduled` 和新调度同时打开。
